Notes for every reader of these sets:

- **The probe's own rule.** `nodes-to-public-ping` (A/fw/14_running_security.txt:231, `index: 13`; its set lines A/fw/16_config_set.txt:333 to :341) admits zone k8s-nodes to the public address 198.51.100.2 for ping and nothing else. The firewall can discard a session as a LAND attack only once a rule has allowed it (the counter is a source NAT allocation result), so without it `deny-all-log` refuses the probe first and the LAND check, the land drill and break-4a show nothing; the first attempt met exactly that. Only this lab renders it (`spec/profile-a.yaml`, `drill: land`), so Chapter 4's rulebase has 25 rules where every other build A revision 2 lab has 24. The chapter should show it in Table 4-1 as the probe's rule.
- **The secondary DNS zones at boot.** dns-auth2's nine secondary zones were all taken by `rndc retransfer` in boot's last step (N/rec-make-up.txt:377 to :385; the step 303 s, :386): BIND backs off the retries of a zone that has never loaded while its primary, behind the firewall, is out of reach, and the second attempt's audit met the internal forward zone still unloaded. This is the harness waiting, not a design element.
- **The pull is captured in part.** Each capture point keeps the pull's first 5000 frames on the registry's port (`tcpdump -c`, T/TRACE.md:194), so the frame counts (T/TRACE.md:173 to :177, 5000 at each point) and the reply bytes (T/verdict.txt:25) are of those frames, not of the whole pull. The whole pull decoded to about 11 MiB at a point, over the text cap. The SYN, its translation and the log line are all in what was kept.
- **Where the pull's frames ran.** T's SYN came in on the bundle's second leg (T/pull/captures/1-fw-ae1-leg2.txt:2, :3) and the registry's SYN-ACK went back to the node on the first (T/pull/captures/1-fw-ae1-leg1.txt:2, :3): the pair member and the firewall each pick a leg by their own hash.
- **MSS across the source NAT.** The node's SYN offers MSS 8960 (its MTU 9000) and leaves on the uplink with the same option (T/pull/captures/2-fw-ethernet1-5.txt:3); the registry answers MSS 1460 (:5), so its segments fit the uplink's 1500. The firewall adjusts the MSS only on ae1.110 (A/fw/16_config_set.txt:52, :53), for the operator's tunnel.
- **The pull's log line is its own.** PAN-OS writes the line at session end, and containerd held the connection open after the pull, so the trace read the log for the first SYN's source port until it appeared (N/rec-make-trace.txt:11, :12, the third read) and judged that line only (T/verdict.txt:26; T/pull/traffic-log.txt:14 to :17, source port 51508). The other three entries in that file (:6, :10, :18; source ports 51514, 51522, 51526) are the pull's other connections, whose SYNs are in the inside captures too (T/pull/captures/1-fw-ae1-leg1.txt).
- **The firewall's NTP picks either resolver.** `show ntp` named dns-res1 in U and A and dns-res2 in HA and RA; both are configured (A/fw/16_config_set.txt:19, :20) and both reached through the ae1.130 service route.
- **The firewall resolves the bastion's name but its ping is not answered.** The service-route check looks the name up through the firewall's DNS (A/fw-edge/fw-dns.txt:1, `PING bastion.ai.tarnwick.example (10.20.3.10) from 10.20.13.1`); the ping itself gets no reply (:4), and only the resolution is judged.
- **Nothing answers on the public address.** The operator's client's HTTPS and SSH probes to 198.51.100.2 printed nothing within curl's time limit (A/fw-edge/operator-public-https.txt and operator-public-ssh.txt are empty; A/verdict.txt:907, :908).
- **containerlab's version check.** The deploy ran with the version check disabled, and containerlab printed `Failed fetching latest version information` (N/rec-make-up.txt:214) in place of a release notice.
- **containerlab's writes on the host.** While the lab ran, containerlab's block in `/etc/hosts` and its SSH configuration file named every node (N/clab-writes-before-down.txt); `make down` removed both (N/host-after-down.txt:11, :12).
