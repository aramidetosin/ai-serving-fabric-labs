Notes for every reader of these sets:

- **The requests run from k8s-cp2, and k8s-cp2 answers them itself.** No population reaches the internet Gateway through the firewall in this chapter (the internet users arrive in chapter 10), so the trace sends its requests from k8s-cp2 with `curl --resolve` pinned to each VIP, and its own datapath answers every Gateway VIP: no SYN to 10.20.11.210 or 10.20.11.220 left the node (T/verdict.txt:7, :31), and the API gateway pod received the request from the Envoy address on the node (T/verdict.txt:9). Say the node answers locally, never that the lease holder saw the request.
- **The refused requests are shown absent from the API gateway pods' captures, not from their access log.** The trace captures every API gateway pod on its own interface for the whole request and finds no request carrying the refused path's marker or the admin hostname (T/verdict.txt:28, :32). The keyed request's line at the API gateway is the captured request itself (T/captures/2-api-gateway-764fd87dc-pmq6j-eth0-payload.txt:101); no set here saves the API gateway's access log for the trace's requests. The access log of a person's request is in A/identity/api-gateway-log.txt.
- **The drill's gaps are counted in probe intervals.** Each echo probe sends one request every 2 s on a new connection and each connect loop one connect every 0.5 s, and a gap runs from the last request answered before both ports were shut to the first sent after it that was answered, by their sent times (R/drills.json; FRAMEWORK.md 4.6). So an echo gap of 4.0 s means one request lost between two answered ones, and 2.0 s means none lost; the slowest answer while cut says whether the one in between waited (2.08 to 2.09 s in passes 1 and 3: a connection's SYN retransmitted once). Quote the counts and the gaps with their interval, never as a failover time to the millisecond.
- **The cut takes effect inside the second KLISH session.** The two pair ports are shut one switch after the other between the timeline's `CUT` and `SHUT` stamps (R/pass1/lease-holder-loss/timeline.txt:2, :3), and the bond keeps a leg until the second. The first failed connect of each pass came 0.4 to 0.8 s before `SHUT` (R/pass<N>/lease-holder-loss/probes/tcp-*.log), so "within X s of both ports shut" in the verdict is measured from the stamp after the second session returned, a little after the node was in fact cut.
- **The firewall moved the internet Gateway's ARP entry too.** No drill probe drives traffic to 10.20.11.220 through the firewall, so the drill records that entry and does not judge it; in every pass it named the new holder's bond MAC while the node was cut, as the other two VIPs' entries did (R/verdict.txt:15 to :17, :35 to :37, :55 to :57).
