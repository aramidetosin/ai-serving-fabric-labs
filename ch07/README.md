# Chapter 7: Inference Gateways with the Kubernetes Gateway API

Lab `sfab-ch07`, the companion lab of the book's Chapter 7, "Inference Gateways with the Kubernetes Gateway API". It runs build A's one-tenant state, Tarnwick (the platform's names under `ai.tarnwick.example`), with serving on, as chapter 6's lab does, and checks the chain from the firewall to the model: the Gateways, the names, the certificates, the callers' keys and sign-in, and the timeouts. The lab audits the Gateway layer, the callers' keys and the identity provider, traces one keyed request through both in-cluster hops with every key replaced by its mark, sends an admin hostname to the users' Gateway, runs three drills (one key from mint to revoke under a probe that must lose nothing, the consumer restriction's default status against the rendered 401, and a silent backend past Envoy's stream idle timeout, then the corrected chain), and ships break-7a.

Status: recorded under build A revision 2 on 2026-10-30 on the second lab host, one deployment from wiped disks with the revision 2 models, placement and Gateway layer (`RESULTS.md`, `audits/INDEX.md`); tested against the stand-ins too (`common/tests/test_ch07.py`, `common/sfab/tests/test_ch07_render.py`, `common/sfab/tests/test_k8s.py`). ## What the spec renders for this chapter

Chapter 6's lab renders the whole serving layer (`ch06/README.md`); this lab renders the same, and the chapter teaches the layer in front of the models.

**The Gateways** (`bootstrap/k8s/50-gateways.yaml`): class `cilium`, two Gateways in the namespace `gateways`, each with its VIP in the ingress VLAN 110 as its address, announced by the ingress node that holds its L2 announcement lease (`31-l2-announcement.yaml`: the policy selects the nodes labelled `node-role.tarnwick.example/ingress` and the interface `bond0.110`; the pools in `30-lb-pools.yaml`). The ingress nodes, k8s-ingress1 and k8s-ingress2, send what leaves from 10.20.11.0/24 by their routing table 110 via 10.20.11.1, so a Gateway's answers leave on the VLAN its VIP is in. Each Gateway has one HTTPS listener on `*.ai.tarnwick.example` with a certificate and key of its own (`gw-internal-tls`, `gw-users-tls`), so a hostname a Gateway carries no route for reaches it and is answered 404 there, and the users' Gateway holds no key of the internal one. With serving on, each listener admits HTTPRoutes only from the namespaces labelled for its Gateway (`allowedRoutes`, `from: Selector`, the label `routes.tarnwick.example/<gateway>: "true"`, the spec's `k8s.allowed_routes`), and the render labels exactly the namespaces whose routes it attaches there: `echo`, `identity`, `inference` and `serving` for the internal Gateway, `echo`, `identity` and `inference` for the users'. The labs without serving (milestone M2, chapters 3 and 4) keep `from: All`.

| Gateway | VIP | Hostnames and paths it answers (Table 7-1) |
|---|---|---|
| `gw-internal` | 10.20.11.200 | `llm.ai.tarnwick.example`: `/models` (the bare prefix, to the API gateway) and `/echo` (the test backend); `admin.ai.tarnwick.example` and `grafana.ai.tarnwick.example`: `/echo`; `serve.ai.tarnwick.example`: the serving recipe's own route, `/<model>` and `/<model>-<copy>`; `id.ai.tarnwick.example`: the identity provider |
| `gw-users` | 10.20.11.210 | `llm.ai.tarnwick.example`: `/models/<route id>`, one rule a model (the uuid5 of the model's name), and `/echo`; `id.ai.tarnwick.example`: the identity provider |

**The names** (`bootstrap/dns-auth1/`, `bootstrap/dns-auth2/`, `bootstrap/dns-res1/`, `bootstrap/dns-res2/`, `bootstrap/ent-dns/`, `bootstrap/ops-dns/`): the authoritative pair, dns-auth1 the primary and dns-auth2 its secondary by transfer, answers the internal view (asked by dns-res1 and dns-res2, the inside hosts' resolvers) with the internal Gateway's VIP and the enterprise view (asked by ent-dns, the corporate resolver) with the users' VIP, each view chosen by the asking resolver's address; only the names the spec lists are published, under `ai.tarnwick.example`, with no wildcard, and the enterprise view holds no admin or infrastructure name. The operator, outside, resolves through `ops-dns` (192.0.2.10, `sfab/resolver` with BIND authoritative, on the uplink router's fourth port), whose public zone publishes no platform name in this state: nothing is published on the public address, so the operator's requests name the internal Gateway's VIP and cross the IPsec tunnel from ops-gw.

**The certificates** (`40-pki.yaml`, `bootstrap/ca/`): cert-manager's CA ClusterIssuer signs one certificate a Gateway, each `*.ai.tarnwick.example` with a key of its own, with the lab's platform intermediate, whose name constraints are `ai.tarnwick.example` and the build's address ranges; the root's key stays on the lab host. `proof.json` lists the leaves `sfab-ca proof` signs on the lab host, some outside the constraints, which verification must refuse.

**The callers and the router** (`60-inference-base.yaml` to `63-inference-policy.yaml`, `render/inference.py`): the API gateway (APISIX 3.9.1, standalone) holds one route a model and one consumer group a caller (`inference.callers`): the applications batch (chat) and helpdesk (staff), each with its keys in Secret `inference/api-keys` (fields `<caller>.<id>`, consumers `<caller>_key_<id>`), an owner, an expiry and a request limit for the whole group; and the people of the enterprise audience, group staff (chat and staff), each person a consumer matched on the verified email of an OpenID Connect token. A route admits the groups of the callers that may call its model. Authentication is multi-auth: key-auth on the `Authorization` header, then the lab's `oidc-consumer` plugin (`common/sfab/render/apisix/oidc-consumer.lua`), which verifies the token against the identity provider's key set (RS256 only), wants the issuer, the API gateway's own client id in its audience and a verified email, and attaches the consumer whose subject is that email. Every refused credential is answered `401 {"message":"Authorization Failed"}` with `WWW-Authenticate: Bearer realm="llm.ai.tarnwick.example"`, so another caller's key reads as none; the router's master key replaces the caller's credential; the access log is one JSON line a request naming the consumer and its caller, with no header in it. The router (LiteLLM v1.104.0) holds one deployment a model on the model's Service. The keys are made in the cluster by the key Job and never printed. Dex v2.46.0 (`57-identity.yaml`, namespace `identity`) stands in for the enterprise's identity provider, published on both Gateways as `id.ai.tarnwick.example`; a person signs in with the password grant (production uses the authorization code flow with PKCE) and asks for the API gateway's audience (`audience:server:client_id:ai-gateway`). The API gateway, the router and Dex run on the ingress nodes. A CiliumNetworkPolicy denies everything in `echo`, `identity`, `inference` and `serving` but the request path (`58-network-policy.yaml`, `63-inference-policy.yaml`); Secrets are encrypted at rest (secretbox) and pod traffic between nodes runs through Cilium's WireGuard. This lab's render adds the per-pod key probe's account (`key-probe`: get and list on the namespace's pods).

**The timeout chain** (Table 7-2), set from the speeds measured for the two models on the GPU nodes' CPUs (`spec/profile-a.yaml` `inference.route`): the router's 2 attempts of 280 s (one retry; a stream may stay silent 60 s) inside the API gateway's upstream read of 600 s, inside the model routes' `backendRequest` and `request` of 620 s, so nothing on the path cuts an answer a server's 512-token slot can hold, and a non-streamed attempt stays below Envoy's 300 s stream idle timeout; Envoy's stream idle timeout is left as the pinned Cilium sets it (the render writes neither of its two keys), which the audit reads from each Gateway's listener and the idle-timeout drill corrects and puts back.

## The audit

`audit.sh` runs chapter 6's audit as chapter 6's lab runs it (chapter 4's audit with the cluster and its security, its Gateways, certificates and populations, chapter 5's `rail-backend` group and chapter 6's `placement` group; the operator's population asks `ops-dns` for its names, which answers none, and the collection saves `ops-dns`'s own state, `common/audit/cmds/resolver.list`), and adds three groups (`common/audit/lib-audit.sh` `audit_gateway_layer`, then `judge.py keys`, `judge.py identity` and `judge.py gateway-layer`, in `common/audit/gwlayer.py` and `common/audit/clustersec.py`):

- **keys** (a quick audit too): for each model route a client of the lab reaches (the users' Gateway from the enterprise client, the internal Gateway from the operator's client through the tunnel, the name pinned to its VIP), a request with no key, one with a key no Secret holds (made in the client from its own random bytes) and one with each other model's key (a key of a caller the route does not admit), each answered 401 with the same message (the cross-key check); then the per-pod key probe, a pod of the key tool in the cluster that sends each model's key (the first key of the first application caller that may call the model: batch's for chat, helpdesk's for staff) to every API gateway pod by its address, 200 on the key's own route and 401 on every other (the per-pod key check). Only each answer's status and body are saved (`keys/`); the keys reach the client through pipes and the probe through its own mounted Secret.
- **identity** (a full audit): from each person's client, the identity provider's discovery document through the person's Gateway; a token with the API gateway's audience and one without (the person's password and the client's secret handed through pipes into a 0600 curl configuration, the tokens kept in 0600 files and never saved: only their claims are), each answered on every model route the client reaches, 200 where the person's caller may call the model and 401 otherwise; the token without the audience and an altered one refused 401 with a Bearer challenge; and the API gateway's access log naming the person's consumer (`identity/`).
- **gateway-layer** (a full audit): the GatewayClass `cilium` Accepted; each Gateway's listener admitting HTTPRoutes from its labelled namespaces only, exactly the namespaces the render labels carrying the label, and its routes Accepted; the hostname and path pairs each Gateway answers equal to the render's (the internal Gateway the bare `/models` prefix and the admin hostnames, the users' Gateway one rule a model, no admin hostname on it); each VIP's lease holder an ingress node (Table 7-3); from the other ingress node, in the VIP's own VLAN, each VIP resolving by ARP and opening TCP 443 and answering no ICMP echo (Example 7-4); each VIP's chain for `llm.ai.tarnwick.example` verifying against the lab root, read from a client the firewall lets reach that Gateway (Example 7-5); `sfab-ca proof` on the lab host, its leaves outside the name constraints refused with openssl's own error line (the recorded verification failure); and the timeout chain as the cluster runs it, from the HTTPRoutes and the API gateway's and the router's ConfigMaps, with the stream idle timeout Cilium's operator wrote into each Gateway's listener (`gateway-layer/cec.json`) beside cilium-config's two keys (Example 7-6, Table 7-2). Its reads, as JSON and as kubectl prints them (`gateways.txt`, `httproutes.txt`, `leases.txt`, `namespaces.txt`), are Example 7-3's.

The cluster's security (`cluster-security/`, chapter 4's audit through M2's cluster checks) is judged in this lab too: the API server's encryption configuration and etcd's stored prefix of a Secret, every Cilium agent's WireGuard status, each Gateway's certificate issuer and key (no two equal), the network policies and a probe pod refused by every policed Service, the edge pods on the ingress nodes, each ingress node's table 110, and the users' Gateway's SYN-ACK leaving its lease holder tagged 110.

## The trace

`trace.sh` is chapter 6's serving trace (`ch06/README.md`), keyed, and not pinned to a copy: the request to `chat` from the enterprise client through the users' Gateway (source port 42706), with the batch caller's key, is captured whole at every API gateway pod and every router pod (2048 bytes a frame) instead of at 66 bytes. Each of those pcaps leaves its guest only on a pipe through `common/trace/keyscrub.py`, which replaces every `Authorization` value, and any token shaped like a key, by its mark under the lab's redaction key, `<redacted hmac:XXXXXXXXXXXX>`, padded to the value's length so every frame keeps its length (the TCP checksum of a changed frame no longer matches its payload), and blanks with `_` each timing value llama-server writes into an answer's JSON (`timings`: milliseconds, milliseconds per token and tokens per second, a rate the repository does not publish); the scrubbed pcap is decoded on the lab host as `<point>.txt` and with `-A` as `<point>-payload.txt`, and `captures/scrub.log` counts the values replaced and blanked. The answers the trace and the drills save as files have the same timing values replaced by `[redacted: throughput]` when the set closes (`common/audit/redact.py`), so their sets carry a `REDACTIONS.md`. `request/key.txt`, `master-key.txt` and `backend-key.txt` name the caller's key, the router's master key and the backend key by field, fingerprint and mark, each read through a pipe from its Secret. The judge (`common/trace/servetrace.py`) reads the marks hop by hop: the caller's key from the Gateway's proxy to the API gateway pod that took the request; the router's master key in its place from that pod to the router, and the caller's key nowhere on that hop; the backend key from the router to the server; and every `Authorization` value in the captures a mark. Then one request from the same client, with no key, to `https://admin.ai.tarnwick.example/echo` (source port 42707): the enterprise view holds no admin name, so the request is pinned to the users' VIP, where the Gateway answers 404 (server `envoy`), the client's SYN is seen at the lease holder, and no API gateway pod receives a request for that hostname. The rest of chapter 6's judgment holds for the copy the router picked: a node-local copy's RPC stays inside its node. `TRACE.md` adds the keys hop by hop with each decode line, and the refusal.

## The drills

`drills.sh` (`common/drill/lib-gwdrill.sh`, `common/drill/gwdrill.py`) runs three drills a pass (`PASSES=3` by default; `idle-timeout` runs in the first pass only, since each run rolls Cilium twice). Every drill checks the Gateway layer whole first and after (every API gateway and router pod Ready, both Gateways Programmed, the test backend ready, in two consecutive polls 5 s apart), pushes each restore before its change, archives the inference and test backend namespaces' Warning events (the `idle-timeout` drill also `kube-system`'s, where Cilium's pods fail their readiness probes while the drill rolls them), runs `audit.sh --quick` and then `gwdrill.py analyze`; every stamp is the lab host's clock.

| Drill | What happens |
|---|---|
| `key-lifecycle` | under the gateway probe (one chat completion every 2 s to chat and every 30 s to staff, the slower model, through the users' Gateway with each model's key, each waiting up to 400 s, which must lose nothing): a Job of the key tool mints `batch.fd00000<pass>`, a new key for chat's caller, into the key Secret; the new key goes to the client, which sends one request every 2 s with it through the users' VIP, while the per-pod probe sends it to every API gateway pod in rounds until each accepts it; the same key on staff's route, at every pod and through the VIP; a second probe pod, holding the key before the revoke, then the revoke, until every pod refuses it. The analysis times the Secret's write, the first 200 through the VIP, each pod's acceptance and the last pod's, each pod's refusal after the revoke and the VIP's last 200, and counts the probe's requests by how they ended (none may fail) |
| `rejected-code` | under the same probe: the API gateway's routes ConfigMap applied as the render makes it but with staff's consumer restriction carrying no `rejected_code` and no `rejected_msg`, until every API gateway pod answers chat's key on staff's route with the plugin's own default; then the rendered routes back, until every pod answers 401 again; the same through the VIP, staff's own key answered there, and the ConfigMap the render's at the end |
| `idle-timeout` | one request from the enterprise client to `https://llm.ai.tarnwick.example/echo` through the users' Gateway while the test backend's processes are stopped with SIGSTOP in their nodes' guests (its pods stay Running and keep accepting TCP, so the backend is silent, not gone) for `silent_s` (330 s), then continued: the status, the time and the server that answered, the listener's stream idle timeout then, and the backend's pod capture (whether it sent a byte, and when the Gateway's proxy closed its connection). Then the corrected chain: Cilium upgraded with helm from the in-lab registry with the rendered values plus both stream idle keys at 600 s (as the spec's `k8s.envoy_stream_idle_s` would render them), its operator, agents and Envoy rolled, and the test backend's route given request and backendRequest timeouts of 420 s and 400 s; the same silence answered 200; then the rendered values and route back, the listener's timeout read again, and the helm values compared with the render's |

The `idle-timeout` drill changes Cilium for the whole cluster while it runs; nothing probes the models through it, and it puts the rendered values back from its EXIT trap whatever happens.

## break-7a

`breaks/7a.yaml`, rendered to `gen/breaks.json`: the second API gateway pod by name is held (a hold file in its sidecar's shared directory, while which `sfab-keys compose` keeps the `apisix.yaml` it has, as a sidecar would that stopped reloading), then a new key for chat's caller, `batch.fa000001`, is minted into the Secret. `make break-7a` records the per-pod probe of the new key (until every pod accepts it, 240 s at most), 20 requests with it through the users' VIP from the enterprise client, and the Secret's fields and fingerprints beside each API gateway pod's sidecar log (which says it is held). It passes when only the held pod never accepts the key and some requests through the VIP fail while others answer. `make heal-7a` deletes the held pod, so its Deployment makes a new one whose sidecar composes from the Secret as it starts, checks every pod accepts the key and every request answers, then, as the break's cleanup, revokes the key, so the Secret holds the lab's first key a caller again before the chapter audit.

## Platform notes for this lab

M1's, chapter 4's, chapter 5's and chapter 6's notes hold here (`dev/m1/README.md`, `ch04/README.md`, `ch05/README.md`, `ch06/README.md`), and M2's note that Cilium 1.19.7 answers no ICMP echo on a Gateway VIP (`dev/m2/README.md`).

What the revision 2 deploys of 2026-10-28 added (their sets are not published, FRAMEWORK.md 4.4):

- **APISIX 3.9.1 turns no OpenID Connect token into a consumer.** Its `openid-connect` plugin attaches none (and with a public key or a key set checks neither issuer nor audience: lua-resty-openidc's bearer verification runs only the exp and nbf validators), and `jwt-auth` finds its consumer by a `key` claim no identity provider issues; hence the lab's `oidc-consumer` plugin, built on the lua-resty-openidc and lua-resty-jwt libraries APISIX ships, under multi-auth after key-auth.
- **Dex v2.46.0 puts the API gateway's client id in a token's audience** only when the requesting client asks for the scope `audience:server:client_id:ai-gateway` and `ai-gateway` lists that client among its trusted peers; without the scope the audience is the requesting client alone.
- **multi-auth answers every refused credential with its own message**, `Authorization Failed`, so the consumer restriction's rejected message is that one too: an unknown key, a token without the audience and a key of a caller the route does not admit read the same 401 (revision 1's per-model keys read `Invalid API key in request`).
- **APISIX's YAML reader cannot read a folded plain scalar** ("found bad indenting"): `sfab-keys compose` writes no folded line (`sfab/keys:3`).
- **An altered token must change its signature's bytes.** A 256-byte RS256 signature is 342 base64url characters whose last carries four padding bits a decoder ignores, so the audit's altered token changes the tenth character from the end.
- **Through the operator's tunnel, an answer larger than one segment needs the MSS clamp** on ae1.110 (`ch04/README.md`, platform notes).

What the recorded deployment showed (paths relative to `audits/`):

- **Envoy's stream idle timeout answers 504 on a complete request.** As rendered, a backend silent for 330 s was cut at the users' Gateway's 300 s stream idle timeout with `504 Gateway Timeout` and the body `stream timeout`, server `envoy`, not the 408 Envoy documents for a stream idle before response headers (`sfab-ch07_drills_20261030T132224Z/pass1/idle-timeout/rendered/headers.txt`:1, `body.txt`:1). A route timeout would read `upstream request timeout`; Cilium 1.19.7 sets none on a route without one.
- **The pinned Cilium writes its stream idle timeout into each Gateway's listener**: 300s as rendered, from cilium-config `http-stream-idle-timeout 300`, with `proxy-stream-idle-timeout-seconds` unset (`sfab-ch07_audit_20261030T130520Z/verdict.txt`:699, :700). The drill raises both keys together, so which one the operator reads is not shown.
- **Rolling Cilium's agents moves the VIPs' leases** (from k8s-ingress1 to k8s-ingress2: `sfab-ch07_drills_20261030T132224Z/pass1/idle-timeout/analysis.txt`:4), and its pods' readiness probes can fail while they start; the idle drill archives `kube-system`'s Warning events after it, as the audit after it would otherwise fail on them.
- **The lease holder answers the echoes a VIP does not** with ICMP redirects (`sfab-ch07_audit_20261030T130520Z/gateway-layer/vip-gw-users.txt`:2, :3): every VIP check stays a TCP connect.
- **llama-server's answers carry its timings** (milliseconds and tokens per second, in a `timings` object the router passes on). The repository publishes no such rate: `redact.py` replaces each value with `[redacted: throughput]` in a saved answer, and `keyscrub.py` blanks each in a keyed capture.
- **A key reaches each API gateway pod on its own schedule**, as kubelet updates the Secret's volume: 23.4 to 71.7 s after the write over three passes, and the routes ConfigMap 25.4 to 76.4 s after its apply (`sfab-ch07_drills_20261030T132224Z/verdict.txt`).
- **Staff takes one request every 30 s under the drills' probe**, as in chapter 6: on the CPUs of the host this lab was recorded on, one every 2 s queued staff's copies past the users' Gateway's 300 s stream idle timeout (`RESULTS.md`, "What the deploys found").
