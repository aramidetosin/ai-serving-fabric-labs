Notes for every reader of these sets:

- **All three Gateway leases sit on k8s-ingress1 here.** Every audit and both traces read gw-inet's, gw-internal's and gw-users's leases on k8s-ingress1 (A/verdict.txt:1210 to :1212; T/TRACE.md:26), so the pair's ports facing the holder are Ethernet13 on both switches and k8s-ingress2's rungs see nothing. No step of this lab places them; chapter 9's recording had gw-inet's on k8s-ingress2.
- **The leg is the hash's.** In this trace the staff's and the internet users' SYNs took leg 1 and the operator's leg 2 (T/verdict.txt:7, :9, :20). Read the leg from the capture; a redeploy can move it.
- **"Silence" at the ISP router reaches the client two ways.** The internet users' connects to inside addresses end either at once with `ERROR:Network_unreachable` (an ICMP answer from a router on the path) or at the 4 s connect timeout, and the same cell can show both from one source port to the next: the users' Gateway cell read `Network_unreachable` in M (M/requests/internet-gw-users-connect-a1.txt:1) and three timeouts in T (T/connects/internet-gw-users.txt:1 to :3); T's internal Gateway flow read two unreachables and a timeout (T/connects/internet-gw-internal.txt:1 to :3). No set captures the ISP router's customer-facing link or an ICMP message, so no line here says why a given attempt got no answer. Write that the ISP router has no route and nothing reached the firewall; do not write that the client saw nothing, or that it always timed out.
- **The ISP-side capture is the ISP router's link to the firewall.** Rung `1-isp-rtr-eth1` is the ISP router's eth1, 198.51.100.8/30 toward the firewall's ethernet1/6 (T/trace.json, A/split-horizon/isp-rtr-ip-route.txt:9). It shows the internet users' allowed SYN (T/captures/1-isp-rtr-eth1.txt:2, :3) and none of their forbidden ones; the router's customer side, where those SYNs arrived, is not captured.
- **The ISP router's link to the firewall was renewed twice.** Its two connected routes on eth1 read an age of about 51 minutes in A, but 33 minutes in HA and 3 minutes in RM, while its other links' routes kept counting from the deployment's start (A/split-horizon/isp-rtr-ip-route.txt:9, :11; HA/split-horizon/isp-rtr-ip-route.txt:9, :11; RM/routers/isp-rtr-ip-route.txt:9, :11): the eth1 routes were installed again at about 02:12 and 03:02, each time about when a trace ended. No set records a link event or why, the trace only runs tcpdump on that port (T/commands.txt:162, :163), and no verdict depends on it: the drills' internet users held every connection with every reply 200 after the first (D/verdict.txt:8), and RT and RM read the same verdicts as T and M. Chapters 9 and 10's recordings show the same renewal later in their runs. Do not quote a route's age.
- **The matrix's silence cells cite a capture the matrix set does not hold.** MATRIX.md:87 says each silence's evidence is "a capture at the hop"; M holds no capture. For the internet users' two Gateway cells the capture is T's (no SYN at any rung, T/verdict.txt:18, :19); for the others the evidence is the router's table and the absent log line in each cell's row. MATRIX.md cites the ISP router's table at line 1, its first line; the table is M/routers/isp-rtr-ip-route.txt:8 to :16 (eight connected and local routes, none into 10.0.0.0/8, no default).
- **"staff's key" in the matrix is the staff model's key.** The internet users' chat cell is asked with inetapp's key (M/verdict.txt:106) and again with the other model's key, staff's, which is helpdesk's key `helpdesk.77a33a1c` (M/verdict.txt:107; N/rec-make-break-11a.txt:8 names it); it is not the staff people's sign-in.
- **The API gateway's log names a caller, not a client.** Its `client` field is the Gateway proxy's address in the cluster (`10.22.5.105`, M/api-gateway/access.txt:31; D/pass1/leaked-key/api-gateway-access.txt:139), never inet-client's 203.0.113.2. The log says who called; where the call came from is the Gateway's and the firewall's to say.
- **A leaked key keeps working until the API gateway reloads it.** In passes 1 and 3 one request sent after the key Secret's write had been made was still answered 200 before the refusals began (D/pass1/leaked-key/requests-revoked.txt:1, :2 against D/pass1/leaked-key/timeline.txt:5; D/pass3/leaked-key/requests-revoked.txt:1, :2); the verdict times the first 401 from the end of the revoke, 0.149 s to 2.41 s (D/verdict.txt:30, :61, :92). Before it was accepted, the new key was refused 401 for up to about 17 s after the mint while the API gateway pods loaded it (D/pass1/leaked-key/requests-minted.txt:1 to :8).
- **The drill's session counts after the tries are not the held load.** The judged count is read while the connections are held and before the tries (8 a zone at the plan's load, 16 at twice it, D/pass1/isolation-under-load/x1/counts-held-*.txt:2, x2/counts-held-*.txt:2). The count read after the tries, recorded and not judged, is 11 to 24 (`counts-tries-*.txt`), because each probe's own connection to the population's own VIP stays listed, still ACTIVE, for a time after it closes (D/pass1/isolation-under-load/x1/sessions-tries-enterprise.txt: 14 entries, every one ACTIVE).
- **The break did not run the ladder.** break-11a records the route and the two cells, not packet tallies: no set captures the rungs while the route was broken. A sentence that every packet tally stayed zero during the break cites no line here; the network layers' configuration is unchanged by the break (B/record/break-patch-models-gw-inet.json touches only the route's rules).
- **The broken staff cell is still a 404, from the layer behind.** With staff's path on the internet Gateway, the matrix's staff request (a GET with no key) passes the Gateway and reaches the API gateway, whose routes take POST alone, and it answers its own 404, `{"error_msg":"404 Route Not Found"}`, with Envoy's `x-envoy-upstream-service-time` header (B/probes/cells-break/requests/internet-staff-request-a1-headers.txt:1 to :6, -body.txt:1; its line in the API gateway's log, B/probes/cells-break/api-gateway/access.txt:43). Healed, it is the Gateway's own empty 404, `content-length: 0`, no upstream header (H/probes/cells-heal/requests/internet-staff-request-a1-headers.txt:1 to :4). Same status, a different layer: the exercise must name the layer, not the code.
- **Key secrecy at depth 0 is not recorded.** The matrix holds no cell for a compromised internet-facing proxy reading another audience's key; Section 1's depth 0 for it is the chapter's reasoning, and the leaked-key drill is the recorded instance of a key used outside its audience.
